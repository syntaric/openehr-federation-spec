= 7a. The REST façade (openEHR ITS-REST)

The federation surface is *not* limited to AQL. A gateway presents the openEHR *ITS-REST* API as a whole - reads *and* writes - so that an application written against a single CDR can be pointed at the gateway unchanged (xref:requirements.adoc#n1[N1]). AQL (xref:aql-facade.adoc[§7]) is the part of that surface where fan-out happens; the rest of the surface is routed to a single node (xref:follow-up-routing.adoc[§12]).

Transparency is only credible if the *boundaries* are stated. This section therefore says both what a gateway MUST expose and what it is *not* expected to federate.

== 7a.1 What the façade federates

[cols="2,1,3"]
|===
| ITS-REST area | Federated? | Behaviour at the gateway

| `+{base}/v1/query/aql+` (Query)
| *Yes - fan-out*
| The subject → `ehr_id` rewrite and multi-node fan-out of xref:aql-facade.adoc[§7]. This is the only *fan-out read* in v1.

| `+{base}/v1/ehr/{ehr_id}+` and `+{base}/v1/ehr/{ehr_id}/…+` (EHR, EHR_STATUS, COMPOSITION, DIRECTORY, CONTRIBUTION, VERSIONED_*)
| *Yes - single-node routing*
| Routed to exactly one node by the rules of xref:follow-up-routing.adoc[§12]. `+{ehr_id}+` in the path is a *node-local* identifier, so the gateway MUST resolve which node it belongs to before forwarding (xref:follow-up-routing.adoc[§12.5]).

| `+{base}/v1/definition/template/…+`, `+{base}/v1/definition/query/…+` (Definition / ADL, stored queries)
| *Partially - not federated in v1*
| A gateway MAY expose these, but MUST route each request to a *single, explicitly chosen* node (xref:follow-up-routing.adoc[§12.6]). It MUST NOT silently pick a node, and MUST NOT present a merged view of templates across nodes as if it were one repository. Fan-out of template upload is OPTIONAL and discussed in xref:follow-up-routing.adoc[§12.6].

| `+{base}/v1/demographic/…+` (DEMOGRAPHIC)
| *No - out of scope*
| The federation model deliberately keeps demographics *outside* the CDR (xref:identity-resolution.adoc[§5.1]); identity is resolved by an MPI / demographic service through the identity binding (xref:identity-resolution.adoc[§5.2], xref:annex-a-ihe.adoc[Annex A]). A gateway MUST NOT federate the openEHR DEMOGRAPHIC API. If it does not expose it at all, it MUST answer `501 Not Implemented`; if it proxies it to a single node, it MUST do so under xref:follow-up-routing.adoc[§12.6] single-node rules and MUST declare this (xref:conformance.adoc[§17]).

|===


== 7a.2 Declaring the surface: `OPTIONS`

A client (and a test harness) needs a machine-readable answer to _"what does this gateway actually do, and what is behind it?"_.

* [[options-root]]A gateway MUST implement `+OPTIONS {base}/+` returning a description of the federation surface: the ITS-REST areas it supports (per §7a.1 above), which are federated vs. single-node-routed, which are unsupported, the dedup mode (xref:deduplication.adoc[§10]), and the gateway's timeout policy (xref:partial-results.adoc[§11.5]). _(xref:requirements.adoc#n30[N30].)_
* The response MUST include the *member endpoints behind the gateway* - the same identifiers usable in a directive (xref:endpoint-directive.adoc[§8]) - each with at least `id`, `organisation`, and `status`. It SHOULD include `product` / `version` and observed `latency` where the gateway tracks them (xref:result-set.adoc[§9.4]).
* The endpoint list is *federation membership information*, not patient data: it MUST NOT be gated on a patient identifier, and it MUST be subject to the gateway's normal authentication (xref:security.adoc[§13]). A deployment MAY restrict the detail returned to unauthenticated callers.
* `OPTIONS` on a *sub-path* (e.g. `+OPTIONS {base}/v1/ehr/{ehr_id}+`) SHOULD return the HTTP methods allowed for that resource, per ordinary HTTP semantics.

.Example `OPTIONS /` response body
[source,json]
----
{
  "federation": {
    "id": "rso-zl",
    "spec_version": "0.3",
    "aql": { "fan_out": true, "endpoint_directive": true, "endpoint_header": true },
    "dedup": { "default": "none", "modes": ["none", "version-identity"] },
    "timeout": { "per_node_ms": 5000, "overall_ms": 15000, "policy": "best-effort" },
    "its_rest": {
      "query": "federated",
      "ehr": "routed",
      "definition": "routed-single-node",
      "demographic": "unsupported"
    }
  },
  "endpoints": [
    { "id": "node_1", "system_id": "cdr1.rso.nl", "organisation": "Org A",
      "status": "active", "product": "VendorX CDR 3.4.1", "latency_ms_p50": 120 },
    { "id": "node_2", "system_id": "cdr2.rso.nl", "organisation": "Org B",
      "status": "active", "product": "VendorY 2026.1", "latency_ms_p50": 310 }
  ]
}
----

== 7a.3 Write responses carry provenance in headers

An AQL result set carries provenance in `meta.endpoints[]` (xref:result-set.adoc[§9]). A *write* has no such envelope: `+POST {base}/v1/ehr/{ehr_id}/composition+` returns a `201` with `Location` and `ETag`, and nothing else.

* [[write-headers]]On every request the gateway routed or dispatched to a single node - including `POST`, `PUT` and `DELETE` - the gateway MUST return the *acting endpoint's identifier* in the `openEHR-federation-endpoint` response header, and SHOULD return the node's `system_id` in `openEHR-federation-system-id`. _(xref:requirements.adoc#n31[N31], xref:result-set.adoc[§9.5].)_
* The gateway MUST pass the node's `Location` and `ETag` through *unmodified* - openEHR uids are never rewritten (xref:requirements.adoc#n22[N22]). Because the `ETag` of a commit is an `OBJECT_VERSION_ID`, it already carries the `creating_system_id`; the headers above are a convenience and an audit aid, not a replacement for it.
* These headers SHOULD also be set on federated AQL responses, listing the endpoints that contributed, but `meta.endpoints[]` remains the *normative* carrier there (xref:partial-results.adoc[§11.1]).
