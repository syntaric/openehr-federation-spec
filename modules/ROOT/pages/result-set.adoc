= 9. Result-set format & origin metadata

== 9.1 Envelope

The result set MUST follow the `{q, columns, rows}` + `meta` envelope (xref:requirements.adoc#n17[N17]). Endpoint columns appear *only* when ENDPOINT attributes are selected; otherwise the row shape is *identical* to running the same query directly on a single CDR (single-CDR compatibility, xref:requirements.adoc#n17[N17]). ENDPOINT attribute aliases resolve any name collision with EHR-derived columns (xref:requirements.adoc#n18[N18]).

The example in §9.3 and the field table in §9.4 are *jointly normative* for the envelope: the table fixes the fields and their obligation level, the example fixes their arrangement. Where the two could be read differently, the table governs. A machine-readable JSON Schema for the envelope is planned for a future release (xref:future.adoc[§18]); until it exists, these two are the contract.

[#columns-provenance]
[IMPORTANT]
.`columns[]` is the gateway's rendering, never a node's
====
`columns[]` MUST be rendered by the gateway from the *client's submitted AQL*, and is *independent* of any column paths a node reports. A gateway MUST NOT pass a node's rendering through (xref:requirements.adoc#n17[N17], xref:conformance.adoc#cp-35[CP-35]).

This is not a stylistic preference. Real CDRs disagree on the same query: for `FROM … c CONTAINS COMPOSITION`, one product reports `c/context/start_time/value` (retaining the FROM alias) and another `/context/start_time/value` (stripping it). In a single-CDR deployment the question does not arise - there is one answer. In a fan-out there are *N* candidate answers for a field the envelope treats as singular, so a gateway that echoes whichever node replied first produces output that depends on response scheduling. A client cannot then match `ORDER BY` terms or projections against a path whose shape depends on which node was fastest.
====

== 9.2 ENDPOINT attribute set

The selectable ENDPOINT attributes are the endpoint/organization provenance fields plus the openEHR-native routing key `system_id`:

[cols="1,2"]
|===
| Attribute | Meaning

| `endpoint_id`
| Stable registry identifier of the Endpoint (xref:requirements.adoc#n19[N19]).

| `organisation` / `organization_id`
| The managing Organization (xref:requirements.adoc#n20[N20]).

| `system_id`
| The node's openEHR logical EHR-system id - the follow-up routing key (xref:follow-up-routing.adoc[§12], xref:requirements.adoc#n21[N21]).

| `url`
| The CDR base URL (from the registry; MAY be omitted from rows and left in `meta`).
|===

Including `system_id` in the row-level attribute set puts the *openEHR-native routing key* in the result, so the Application tier can route a follow-up without a second registry lookup (xref:follow-up-routing.adoc[§12]).

== 9.3 Example

[source,json]
----
{
  "q": "SELECT p/id AS endpoint_id, p/system_id AS system_id, c/uid/value AS composition_id FROM ENDPOINT p [\"node_1\",\"node_2\"] CONTAINS EHR e CONTAINS COMPOSITION c WHERE e/ehr_status/subject/external_ref/id/value = '12345'",
  "columns": [
    { "name": "endpoint_id",    "path": "p/id",        "type": "STRING" },
    { "name": "system_id",      "path": "p/system_id", "type": "STRING" },
    { "name": "composition_id", "path": "c/uid/value", "type": "STRING" }
  ],
  "rows": [
    { "endpoint_id": "node_1", "system_id": "cdr1.rso.nl", "composition_id": "8849182a-1d4b-4e3d-a3f3-f303d2f4f34b::cdr1.rso.nl::1" },
    { "endpoint_id": "node_2", "system_id": "cdr2.rso.nl", "composition_id": "6ba7b810-9dad-11d1-80b4-00c04fd430c8::cdr2.rso.nl::1" }
  ],
  "meta": {
    "complete": true,
    "endpoints": [
      { "id": "node_1", "node_id": "node_1", "system_id": "cdr1.rso.nl", "organisation": "Org A",
        "url": "https://ehr.hospital-a.example/openehr/v1", "status": "active",
        "latency_ms": 118, "product": "VendorX CDR", "version": "3.4.1", "row_count": 1 },
      { "id": "node_2", "node_id": "node_2", "system_id": "cdr2.rso.nl", "organisation": "Org B",
        "url": "https://ehr.clinic-b.example/openehr/v1", "status": "active",
        "latency_ms": 306, "product": "VendorY", "version": "2026.1", "row_count": 1 },
      { "id": "node_3", "node_id": "node_3", "organisation": "Org C",
        "status": "excluded" }
    ]
  }
}
----

Each `composition_id` is an `OBJECT_VERSION_ID` whose middle segment is the `creating_system_id` (`cdr1.rso.nl`, `cdr2.rso.nl`) - this is what xref:follow-up-routing.adoc[§12] routes on.

`node_3` shows a reported-but-not-queried member: this query was *directed* at `node_1` and `node_2`, so the directive excluded it (xref:partial-results.adoc#endpoint-status[§11.1]). Had the query been undirected and localization simply not named it, its status would be `not-localized` instead. Neither clears `meta.complete`, which is `true` here because every node that *was* in scope answered.

[#endpoint-meta]
== 9.4 `meta.endpoints[]` fields

`meta.endpoints[]` is the per-node record of what happened, and it is the *normative* carrier for coverage information (xref:partial-results.adoc#endpoint-status[§11.1]). Every in-scope node appears, whether or not it contributed rows.

[cols="1,1,3"]
|===
| Field | | Meaning

| `id`
| MUST
| The `endpoint_id` - the stable registry identifier of the endpoint that was addressed (xref:terminology.adoc#endpoint-id[§ The four identifiers]).

| `status`
| MUST
| One of the statuses in xref:partial-results.adoc#endpoint-status[§11.1].

| `node_id`
| SHOULD
| The owning node (xref:terminology.adoc#node-id[§ The four identifiers]). Distinguishes two endpoints of the same node.

| `system_id`
| SHOULD
| The node's openEHR `system_id`, where known (xref:terminology.adoc#system-id[§ The four identifiers]).

| `organisation`
| SHOULD
| The managing Organization (xref:requirements.adoc#n20[N20]).

| `error`
| MUST, when `status` is an error
| The node-reported or gateway-reported error (xref:partial-results.adoc#http-status-mapping[§11.2]).

| [[meta-latency]]`latency_ms`
| MUST
| Wall-clock time the *gateway* observed for its request to this endpoint, in milliseconds. For a `time-out` endpoint this is the elapsed time at abandonment (xref:partial-results.adoc#timeouts[§11.5]). This is the gateway's own measurement, not the node's self-report. _(xref:requirements.adoc#n40[N40].)_

| [[meta-version]]`product` / `version`
| SHOULD
| The node's product name and version, as the gateway knows them - from the registry, from the node's own capability/`OPTIONS` response, or from cached discovery. Absent when unknown; a gateway MUST NOT invent them. _(xref:requirements.adoc#n40[N40].)_

| `row_count`
| SHOULD
| Rows this endpoint contributed *before* federation-level `DISTINCT`, dedup (xref:deduplication.adoc[§10]) and `LIMIT` (xref:partial-results.adoc#aggregation-and-ordering[§11.6]). Makes suppression auditable.

| `url`
| MAY
| The CDR base URL. MAY be omitted from rows and left here.
|===

`meta` itself MUST additionally carry `complete` (xref:partial-results.adoc#completeness-flag[§11.4]) and SHOULD carry the effective timeout budget in force for the request (xref:partial-results.adoc#timeouts[§11.5]).

Why xref:result-set.adoc#meta-latency[latency] and xref:result-set.adoc#meta-version[version] belong here: a federated query is only as good as its slowest and its oldest member, and an operator debugging *"why is this slow"* or *"why does node 3 not support this AQL feature"* otherwise has to correlate gateway logs by hand. The same fields appear in `+OPTIONS {base}/+` (xref:rest-facade.adoc#options-root[§7a.2]) - `product` and `version` as the same two separate fields, latency as an aggregate over recent requests rather than this request's measurement.

[#response-headers]
== 9.5 Responses with no envelope: headers

An AQL response carries `meta`. A *write* or a *routed ITS-REST read* does not - a `201 Created` has only headers. The provenance that `meta.endpoints[]` carries for a query is therefore carried by the `openEHR-federation-endpoint` / `openEHR-federation-system-id` response headers on those requests; see xref:rest-facade.adoc#write-headers[§7a.3] and xref:requirements.adoc#n31[N31].
