= 5. Patient identity resolution (federated patient management)

== 5.1 Why federation is not keyed on `EHR_STATUS.subject`

Storing a national identifier (the BSN) in `EHR_STATUS.subject.external_ref.id` is technically undesirable, for the reasons the MPI advisory sets out in §3, each of which this specification adopts:

. *Directly identifying → breach amplification.* All clinical content becomes directly traceable to one person, so "the impact of a data breach becomes exponentially greater" (advisory §3.1.2.1).
. *It breaks the demographic/clinical separation.* The openEHR reference model "expects identifying data to be located outside the CDR in a Demographic Service or MPI"; `EHR_STATUS.subject.ID` is "intended as a *reference* to a demographic record, not as an identifying personal number itself" (advisory §3.1.2.2). In openEHR RM terms (cited to the RM, not the advisory), `EHR_STATUS.subject` is a `PARTY_SELF` whose `external_ref.id` is an `OBJECT_REF`: a pointer, not a value store.
. *Versioning makes it permanent/unremovable.* openEHR's versioning means the value "permanently ends up in every version" and is "no longer safely removable", creating a "life-long identifier footprint in all versions" (advisory §3.1.2.3, §3.1.4).
. *It blocks pseudonymisation / secondary use.* Because the id "cannot be removed without damaging the EHR structure … this blocks secure secondary use" (advisory §3.1.2.4); using the BSN as `subject_id` means "you lose the possibility of secure pseudonymization" (advisory §3.1.2.2).
. *It fails for patients without a BSN and for international patients.* The approach is "not applicable to international patients or patients without a BSN" and "makes the openEHR environment inflexible … outside the Dutch context" (advisory §3.1.2.5).
. *It mishandles the identity lifecycle.* It "bypasses the demographic layer", and in merges/splits "the BSN remains unchanged, causing incorrect identities to become permanently embedded" (advisory §3.1.2.6).

The conclusion adopted here is that *the BSN belongs in an MPI or demographic service, not in the CDR* (advisory §3.1.4): the MPI/demographic component holds all personally identifying information while the CDR stores only clinical data (advisory §3.2). Federation therefore keys on the local `ehr_id`, and the `subject → ehr_id` mapping is performed by an identity service outside the query.

== 5.2 Resolution model

* The Federation Tier MUST resolve `<patientId>` (with its issuing namespace) to a set of `{node, local ehr_id}` using an *identifier cross-reference service* (proposed binding: *IHE PIXm* `$ihe-pix`, `sourceIdentifier=<patientId>`, `targetSystem=<the domain's ehr_id system>`, with *XCPD* for cross-community discovery and *PMIR* for identity lifecycle as needed). Resolution MUST occur *outside AQL* (xref:requirements.adoc#n3[N3]).
* For an *undirected* query, the candidate node set and the consent decision MUST come from a *localization / record-locator service* (proposed binding: IHE *XCPD*; regional alternative in xref:annex-b-dutch-gf.adoc[Annex B]). The locator's internals are out of scope (xref:requirements.adoc#n4[N4], xref:localization.adoc[§14]).
* A national identifier (BSN) MUST NOT be *required* to be stored in `EHR_STATUS.subject` at any node. If a federated result includes a `subject` column, its value is the *re-injected resolution input*, not data read from a CDR (xref:requirements.adoc#n5[N5], xref:aql-facade.adoc[§7]).
* Nodes where the patient is `not-resolved`, or where consent is denied, MUST be recorded in metadata and MUST NOT be queried, and MUST NOT fail the overall query (xref:requirements.adoc#n6[N6]).

`{node, local ehr_id}` denotes a *set of per-node triples*: for each candidate node, the patient's local `ehr_id` (or _not-found_). Only nodes with a resolved `ehr_id` are dispatched to in Step 2. Consent is discussed further in xref:security.adoc[§13.2] and xref:localization.adoc[§14] (in many realisations the localization service returns the consent decision together with the node list).

== 5.3 The demographic input may itself be pseudonymised

Nothing in this model requires `<patientId>` to be a BSN. Because resolution happens outside AQL (§5.2), the presented identifier MAY be a *pseudonymised* id that a node resolves to a local `ehr_id` before running standard AQL - so a node need store *no BSN in the CDR*. A concrete worked example is in *xref:annex-b-dutch-gf.adoc[Annex B §B.7]*.
