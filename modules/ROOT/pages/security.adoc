= 13. Authentication & Authorization

[[identity-conveyance]]
== 13.1 Identity conveyance (client → gateway → node)

* The client MUST authenticate to the Federation Tier (xref:requirements.adoc#n25[N25]). The Tier authenticates *onward* to each node and MUST *propagate the client's identity*, because - per the White Paper - the source server needs it both to enable appropriate audit records on the source server and to allow the source server to make appropriate security decisions about what records are made available.
* The default mechanism is *OAuth 2.0* (RFC 6749) using the *client-credentials* grant with a *signed JWT client assertion* (RFC 7523 §2.2, `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`): a node hosts an OAuth token endpoint that authenticates the gateway via that assertion, with the gateway's signing keys published as a *JWKS* (RFC 7517) resolvable by the node. A regional federated-identity stack MAY be used instead (xref:annex-b-dutch-gf.adoc[Annex B]).
* [[jwks-discovery]]*The JWKS must be discoverable, not merely published.* The gateway MUST report the JWKS location as `federation.auth.jwks_uri` in `+OPTIONS {base}/+` (xref:rest-facade.adoc#options-root[§7a.2]), so a node can obtain the keys it verifies against without an out-of-band arrangement. This specification does not mandate where the key set is hosted - a deployment is free to serve it from wherever its PKI already lives - only that the gateway says where that is. _(xref:requirements.adoc#n25[N25], xref:requirements.adoc#n30[N30].)_

[NOTE]
====
*End-user scoping is not yet specified.* The exchange above authenticates the *gateway as a service*; it does not by itself convey an end-user. Where a node's release decision depends on _who_ is asking (not merely _which system_), a deployment needs an additional mechanism - candidates are OAuth 2.0 *Token Exchange* (RFC 8693, conveying the end-user as `subject_token` with the gateway as `actor_token`), or an OpenID Connect `id_token` conveyed alongside the client assertion. This specification does not yet mandate either; a future revision is expected to settle it (xref:future.adoc[§18]). Until then, deployments requiring end-user-scoped authorization SHOULD follow their regional stack (xref:annex-b-dutch-gf.adoc[Annex B]).
====

[NOTE]
====
Deployments that also expose FHIR endpoints will find *SMART App Launch: Backend Services* to be a compatible profile of this exchange - it is the same RFC 7523 client assertion with FHIR-specific scopes and discovery layered on top. Conformance to this specification neither requires nor implies SMART conformance, and the FHIR-specific parts (`system/…` scopes, `.well-known/smart-configuration`, CapabilityStatement) do not apply to an openEHR CDR.
====

== 13.2 Per-node authorization and consent

*Consent is enforced at the node.* Each node performs its *own* authorization and *consent/opt-out* checks before releasing data - each participant is responsible for checking consent or opt-out before providing health information of a given patient (xref:requirements.adoc#n27[N27]). This check is unconditional: a node MUST perform it *whether or not* the gateway, a localization service or a consent service already formed a view upstream. A node MUST NOT treat its own appearance in a localization result as evidence that consent was given.

Access decisions requiring information *not visible* to the gateway MUST be *delegated to the source CDR*; the gateway MUST NOT be the sole authority for releasing sensitive data (xref:requirements.adoc#n26[N26]).

=== 13.2.1 Optional pre-filtering, and why it is not the gate

Some deployments can answer the consent question *before* dispatch, from a consent service that is either standalone or folded into localization. Where such a service exists the gateway MAY use its decision to drop nodes at Step 1 and MUST report them as `consent-denied` (xref:requirements.adoc#n27a[N27a], xref:partial-results.adoc#endpoint-status[§11.1]). This is an *efficiency and data-minimisation* measure - it avoids dispatching a query that would be refused anyway, and avoids disclosing to a node that the patient was asked about - not a substitute for the node's check.

It is not the gate, for three reasons:

. *Not every federation has one.* A pure record-locator (IHE XCPD ITI-55) reports which communities hold data; it says nothing about release. A deployment with no consent service is fully conformant - Step 1 simply carries no consent signal.
. *The upstream view can be stale or incomplete.* Consent can be withdrawn between Step 1 and dispatch, and a node routinely holds local consent state, care-relationship context and data-sensitivity classifications that no central service sees.
. *Only the node knows what it is about to release.* Consent is frequently scoped - to a data category, a purpose of use, a requesting organization - and that scope can only be applied against the actual data in hand (xref:requirements.adoc#n26[N26]).

[IMPORTANT]
====
A federation MUST NOT be designed so that consent is enforced *only* by a localization or consent service upstream of the nodes. Localization answers _where data might be_; consent answers _whether it may be released_. A deployment that collapses the two has no enforcement point left when the localizer is wrong, stale, bypassed, or - in a directed query (xref:endpoint-directive.adoc[§8]) - not consulted at all.
====

A *directed* query makes the last point concrete: `FROM ENDPOINT` selects the node set independently of patient resolution (xref:requirements.adoc#n11[N11]), so localization need never run. If consent rode only on localization, a directed query would bypass it entirely. Under xref:requirements.adoc#n27[N27] it does not: the node checks regardless of how it came to be addressed.

== 13.3 Regional realisation

A deployment MAY realise this handoff with a regional authentication/authorization/consent stack instead of the plain RFC 7523 exchange of <<identity-conveyance,§13.1>>, provided xref:requirements.adoc#n24[N24]–N27 still hold. The Dutch Generic-Functions realisation *profiles* that exchange - same OAuth 2.0 + RFC 7523 base, with a Verifiable Presentation carried in the authorization grant, sender-constrained tokens (DPoP), policy-based authorization and a national consent service - and is documented in *xref:annex-b-dutch-gf.adoc[Annex B (§B.4–§B.6)]*.

Note that this specification does *not* mandate sender-constraining (DPoP, RFC 9449) in the base profile; it is a property of the GF realisation. Deployments crossing organizational trust boundaries SHOULD consider whether bearer-token replay is an acceptable risk in their setting.
