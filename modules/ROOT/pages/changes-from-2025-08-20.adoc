= Changes from the 2025-08-20 proposal

This note accompanies *_Proposal for Federation Tier with AQL - revised_* and records what changed relative to the original openEHR International Federation Working Group proposal _"Proposal for Federation Tier with AQL"_ (2025-08-20). The revised specification itself is written as a standalone spec and does not narrate this history; that history lives here.

== Headline (breaking) changes

[cols="1,4,2,3"]
|===
| # | Change | Where in the revised spec | Rationale

| C1
| *Federation is keyed on the per-node local `ehr_id`, not on `EHR_STATUS.subject`.* The gateway resolves `subject → ehr_id` *outside* AQL and dispatches *standard, non-federated* AQL per node.
| xref:reference-flow.adoc[§4], xref:identity-resolution.adoc[§5], xref:requirements.adoc[§6] (N3, N7), xref:aql-facade.adoc[§7]
| MPI advisory §3 (storing an identifier in `EHR_STATUS.subject` is undesirable); RSO "Record identification".

| C2
| *The federated example that filtered `WHERE …/ehr_status/subject/external_ref/id/value` at the node level is removed.* `subject` now appears only as _façade input_, rewritten to `ehr_id` before dispatch.
| xref:aql-facade.adoc[§7] (before→after)
| Internal consistency: the old example keyed federation on `subject`.

| C3
| *The gateway is defined as a transparent façade* - a client can query and follow up without knowing it is federated; the API is a conformant openEHR Query API.
| xref:index.adoc[§1], xref:architecture.adoc[§3.2], xref:requirements.adoc#n1[N1]
| HL7 Intermediaries White Paper (transparency).

| C4
| *Storing a directly identifying patient identifier in `EHR_STATUS.subject` is no longer part of the federation model* (storing the BSN there was the RSO interim approach). Identity is resolved in an MPI/demographic layer; no such identifier need be stored in the CDR.
| xref:identity-resolution.adoc[§5], xref:requirements.adoc#n5[N5]
| MPI advisory §3; RSO's own "Hide"/external-ref migration note.

| C5
| *Identity / localization / addressing are bound to IHE profiles* (PIXm, PDQm, XCPD, PMIR, mCSD) as the *proposed binding*, with the *Dutch Generic Functions* as a regional alternative in an informative annex.
| xref:identity-resolution.adoc[§5], xref:localization.adoc[§14], xref:addressing.adoc[§15], xref:annex-a-ihe.adoc[Annex A], xref:annex-b-dutch-gf.adoc[Annex B]
| Consolidated design decision; MPI advisory §4.

| C6
| *Follow-up read _and_ write routing is specified*, provenance-honest: rows carry an endpoint identifier and routing uses the `creating_system_id` inside the `OBJECT_VERSION_ID`; *openEHR uids are never rewritten*.
| xref:result-set.adoc[§9], xref:follow-up-routing.adoc[§12] (N21–N24)
| Intermediaries White Paper (routing follow-ups); Exchange-Routing IG (self-routing base URL).

| C7
| *Four previously-absent areas are added:* authN/authZ handoff (xref:security.adoc[§13]), localization vs record-locator split (xref:localization.adoc[§14]) and addressing (xref:addressing.adoc[§15]), follow-up routing (xref:follow-up-routing.adoc[§12]), and a Connectathon-style test guide (xref:testing.adoc[§16]–xref:conformance.adoc[§17]).
| §12–§17
| Gaps flagged in the change brief.

| C8
| *The federation surface is the whole ITS-REST API*, read and write - not AQL alone - with the unsupported parts named (DEMOGRAPHIC; Definition management is single-node in v1), the vendor `/rest/openehr` prefix removed in favour of a deployment-chosen base URL, both EHR addressing forms supported, and `+OPTIONS {base}/+` added so a gateway describes itself and the endpoints behind it.
| xref:rest-facade.adoc[§7a] (N28–N32), xref:requirements.adoc#n43[N43]
| Review meeting: transparency has to cover reads and writes, and the prefix is vendor-specific.

| C9
| *Identifier hygiene is specified beyond `subject`.* In the query the gateway composes, a node is located by the `ehr_id` and nothing else identifying: predicates and projections over `PARTY_IDENTIFIED`/`DV_IDENTIFIER`, `PARTY_RELATED` and `ENTRY`-level `subject`, plus the path, query string and headers, are all in scope, and a query that cannot be brought into that state is rejected rather than forwarded. Write payloads are *explicitly out of scope* - a commit body is archetyped clinical content and passes through unmodified. The node's obligation is restated as an *interface* one (be invocable on `ehr_id`; have some way to exchange a patient identifier for it) with no mandate on what a node stores.
| xref:identity-resolution.adoc#identifier-hygiene[§5.4], xref:identity-resolution.adoc#node-obligation[§5.5] (N33, N34)
| Review meeting: the `subject` rewrite alone still leaks; and the spec should not legislate node-internal storage.

| C10
| *Completeness, timeouts and cross-node result shaping are made normative.* Best-effort is the declared default with a `meta.complete` flag; per-node and overall timeout budgets are required and discoverable; `ORDER BY` + `LIMIT` is re-applied at the Tier to give the true global top `n`; `OFFSET` must be rejected or computed correctly; undirected aggregates must be refused with a reason, never answered with per-node rows.
| xref:partial-results.adoc#best-effort[§11.4]–§11.6 (N37–N39)
| Review meeting: timeouts and the limit/order/aggregate interaction were left to implementers and are not safely inferable.

| C11
| *The four identifiers are pinned down* - `node_id`, `endpoint_id`, `system_id`, `creating_system_id` - *defined* in the reader's guide (xref:terminology.adoc#the-four-identifiers[§ The four identifiers]) and with which-one-routes-what made *normative* in xref:identifiers.adoc[§12a]. The consequences are worked through: dedup must not send a write to a node holding an imported copy, an `ehr_id` claimed by two nodes is a `409` and an integrity incident rather than a guess, and *node-admission* conditions (UUID `ehr_id` s, no reuse, no foreign-`ehr_id` adoption, unique `system_id`) prevent the collision in the first place. Because admission is governance rather than routing, those conditions live in their own section, xref:membership.adoc[§12b Federation membership], not inside the routing rules that depend on them.
| xref:terminology.adoc#the-four-identifiers[§ Terminology], xref:identifiers.adoc[§12a], xref:membership.adoc[§12b], xref:deduplication.adoc#update-routing-hazard[§10.3], xref:follow-up-routing.adoc#ehr-id-routing[§12.5] (N36, N41, N42, N42a)
| Review meeting: these four were being conflated, and the failure mode is a mis-routed write.

| C12
| *Endpoint targeting is supported both in and outside the AQL.* The gateway must accept `FROM ENDPOINT` *and* the `openEHR-federation-endpoint` request header (a header, never a query parameter); a client needs only one. Conflicting node sets in one request are rejected rather than merged. Provenance is carried on write responses as headers, and `meta.endpoints[]` gains `latency_ms`, `product`/`version` and `row_count`.
| xref:endpoint-directive.adoc#header-alternative[§8.4] (N35), xref:result-set.adoc#endpoint-meta[§9.5] (N40, N31)
| Review meeting: stored and user-authored AQL should not have to be rewritten to retarget it; and writes have no `meta` to carry provenance.
|===

[#its-rest-alignment]
== 0.4.0: alignment with openEHR ITS-REST, and published schemas

Answering the question _"is the federated AQL response not standard openEHR?"_ surfaced something no earlier review had noticed: *most of the result envelope was already normatively defined by openEHR ITS-REST, and this specification never said so.* xref:result-set.adoc[§9] asserted a `{q, columns, rows}` + `meta` envelope as though inventing it, and 0.3.1 made that worse by declaring its own example and table "jointly normative" for the whole structure - which this specification does not get to be.

The remedy is the same in each case: *cite the standard that already exists, and scope this specification's contract to what it actually adds.* Bound release: *ITS-REST Release-1.1.0* (19 July 2026) - a named release rather than `latest`, because a specification that cites a moving target is not a contract.

[cols="1,4,2,3"]
|===
| # | Finding | Where in the spec | Disposition

| F1
| *`meta` extension is conformant.* ITS-REST declares `ResultSetMetadata` with `additionalProperties: true`, so `complete`, `endpoints[]`, `timeout` and `dedup` are legitimate extensions of a standard open object - no tension with xref:requirements.adoc#n1[N1]. The specification never said this, so an implementer could not tell.
| xref:result-set.adoc#its-rest-relationship[§9.1]
| *Stated.* The reassuring finding, and the one most worth writing down.

| F2
| *`name` was missing.* ITS-REST has five top-level members; N17 mandated four and never mentioned `name`. Minor - it is optional and meaningful only for stored queries - but xref:rest-facade.adoc[§7a.1] lists `+{base}/v1/definition/query/…+` as an exposed area, so stored queries *are* in scope, and a gateway built strictly to N17 omitted a standard member.
| xref:requirements.adoc#n17[N17], xref:result-set.adoc#its-rest-relationship[§9.1]
| *Adopted by reference.* N17 now cites the ITS-REST member list rather than re-enumerating it, so the list cannot drift from ITS-REST again.

| F3
| *The §9 example contradicted ITS-REST on `rows`.* The example serialised rows as *objects* keyed by column name; ITS-REST defines `ResultSetRow` as an *ordered array of values*. Not a documentation nit: a wire-format divergence in the one artifact 0.3.1 called normative, on which two vendors reading the two documents would have serialised differently.
| xref:result-set.adoc#example[§9.4], xref:requirements.adoc#n17[N17], xref:conformance.adoc#cp-35[CP-35]
| *Resolved in favour of ITS-REST; the example was wrong and is corrected.* The `columns[]`/row correspondence is now positional, which makes the xref:result-set.adoc#columns-provenance[§9.2] provenance rule *more* load-bearing, not less - a client matching `ORDER BY` terms now depends on column order as well as path. Both reference implementations emitted objects and are corrected to match.

| F4
| *The underscore convention was unstated.* Standard `meta` fields are `_`-prefixed and the federation's additions are not. That is correct - the prefix marks openEHR-defined fields - but the specification never said so, and an implementer had no way to know `_complete` was not intended.
| xref:result-set.adoc#its-rest-relationship[§9.1], xref:requirements.adoc#n17[N17]
| *Stated normatively.* The `_` prefix is reserved to openEHR; federation additions are never prefixed.

| F5
| *`latency_ms` was an unconditional MUST.* N40 and the §9.5 table required it of every endpoint, including those reported `excluded` or `not-localized` - which were *never asked*, and so were never timed. Writing the schema is what exposed it: the rule as written obliged a gateway to invent a measurement.
| xref:result-set.adoc#endpoint-meta[§9.5], xref:requirements.adoc#n40[N40]
| *Scoped to dispatch.* Required for `active`, `offline` and `time-out`; MUST be omitted rather than invented for the statuses settled before any request existed to time - including `not-resolved`, which is *in scope* (so it clears `complete`) yet was never dispatched to.

| F6
| *Two `OPTIONS` keys were required in prose but absent from the example.* §11.4 requires all-or-nothing completeness be opt-in per request via a named header, and §10 gives dedup a selecting header; the 0.3.1 example declared `all_or_nothing: true` without saying how to select it, and omitted `dedup.request_header`. Both reference implementations emit them.
| xref:rest-facade.adoc#options-root[§7a.2]
| *Added to the example*, and `opt_in` is now conditionally required by the schema whenever `all_or_nothing` is `true`.

| F7
| *The membership status vocabulary was undefined.* §7a.2 said what the `OPTIONS` endpoint status is *not* (the §11.1 per-query vocabulary) but never said what it *is*, implying a closed set that does not exist.
| xref:rest-facade.adoc#endpoint-membership-status[§7a.2]
| *Declared open.* It is a free-form string; `active` is conventional. Fixing a vocabulary is a membership-lifecycle question this release does not specify (xref:future.adoc[§18]). The two schemas model the two statuses as genuinely different types - one a closed seven-value enum, the other an unconstrained string - so the distinction is now enforceable rather than merely asserted.
|===

*Two JSON Schemas are now published and enforced in CI* (xref:future.adoc[§18] previously promised them):

* xref:attachment$federated-result-set.schema.json[`federated-result-set.schema.json`] - the result envelope. It does not restate `RESULT_SET`; it inlines a constrained subset of the ITS-REST definitions, each commented with its source, and adds the federation's `meta` constraints. Inlined rather than `$ref`-ed by URL so validation is self-contained and CI does not depend on a third-party site being reachable.
* xref:attachment$options-root.schema.json[`options-root.schema.json`] - the `OPTIONS` body, which has *no* upstream standard and is therefore normative in this specification alone.

`tools/check-schemas.sh` validates every whole-instance `[source,json]` block in the specification against the schema that governs it, and compiles both schemas. It would have caught F3 automatically, and did catch F5 and F6 while being written.

*This release is 0.4.0, not 0.3.2:* correcting `rows` changes the wire contract, so `federation.spec_version` moves from `"0.3"` to `"0.4"`.

== Other notable edits

* *Result set:* `system_id` added to the selectable ENDPOINT attribute set, so a row can carry the openEHR-native routing key (xref:result-set.adoc[§9]).
* *Deduplication:* the imported-composition case (same `object_id`, two `creating_system_id`s) is now handled by an opt-in VERSION-identity dedup (xref:deduplication.adoc[§10]).
* *Partial results:* the endpoint status set is extended and mapped to HTTP status codes aligned with the Exchange-Routing IG; "patient found nowhere" is a `200` with empty rows, not a `404` (xref:partial-results.adoc[§11]).
* *Diagrams:* the two reference-flow sequence diagrams are authored in PlantUML (`diagrams/*.puml`) and embedded as rendered images.
* *Spec vs regional realisation:* all Dutch-specific detail (Mitz/OTV, NVI, LRZa, `did:web`/VC/DPoP, Rego/`mitz_consent`, pseudonymised-BSN localization) and the ACP/Vitaly worked example are confined to the informative xref:annex-b-dutch-gf.adoc[Annex B]; the normative body names only abstract roles and their proposed IHE binding (xref:scope.adoc[§2.4]).
