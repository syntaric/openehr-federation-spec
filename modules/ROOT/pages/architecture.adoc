= 3. Architecture & Tiers

== 3.1 The three tiers

The federation is a layered, distributed system:

* *Application tier* - end-user applications. They send AQL and consume the combined result set; they interpret and present results and initiate follow-up reads/writes (xref:follow-up-routing.adoc[§12]).
* *Federation Tier* - the technically transparent intermediary. It (a) accepts a conformant openEHR Query API request, (b) resolves the patient identifier to `{node, ehr_id}` *outside AQL*, (c) dispatches *standard* AQL keyed on `ehr_id`, (d) combines and annotates results, and (e) routes follow-up reads/writes to the owning node. It maintains the *registry* (organizations, endpoints, and `system_id`/`creating_system_id` → CDR base URLs) that makes routing possible (xref:requirements.adoc#n21[§6/N21]).
* *Node tier* - a member openEHR *CDR* and its *Query (AQL) API*. A node runs *ordinary* openEHR queries scoped to a single `EHR`; it does *not* need to know it is part of a federation

== 3.2 Transparent-intermediary principle

The gateway follows the transparent-intermediary model of the Intermediaries White Paper: the intermediary performs the search across the servers and collates the response so the client need not know about the multiple contributing sources. Two consequences are normative here:

* The client interface MUST be a *conformant openEHR Query API*, and more broadly a conformant *ITS-REST* surface (xref:requirements.adoc#n1[§6/N1], xref:rest-facade.adoc[§7a]); the client neither sends nor needs any federation-specific syntax to run a basic patient query or a follow-up.
* Transparency is *conditional on completeness*: when a node is dropped (unresponsive, timed out, not-resolved, consent-denied), the gateway MUST make that visible in metadata - the default strategy is *best-effort with an explicit `meta.complete` flag* (xref:partial-results.adoc#best-effort[§11.4]) - so the consumer is not silently misled.
* Transparency is *bounded, not universal*: where the gateway cannot behave as a single repository - federated demographics, cross-node object creation, `OFFSET` paging, undirected aggregates - it MUST say so (via `OPTIONS`, xref:rest-facade.adoc#options-root[§7a.2]) or refuse the request, rather than return an approximation the client cannot detect. *A wrong answer is a worse failure of transparency than an honest refusal.*
